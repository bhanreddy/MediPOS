# Release and rollback gates

1. Run the PostgreSQL CI workflow, web and mobile builds, and the desktop package checks for the exact release revision. Keep a signed-off copy of the prior compatible backend and frontend artifacts.
2. Verify backup credentials, off-host retention, restore validation, and the database role and extension manifest in an isolated environment. Review legacy checkpoint cutover status before deploying code that requires PostgreSQL to be canonical.
3. Rehearse the exact hosting target and database topology with staged synthetic records. Verify CORS preflights, authentication, health, two-store checkout, payments, printing, prescription controls, and offline replay. Confirm the platform's memory, connections, ingress limits, and authenticated throughput under expected peak load. Separate devices, stores, replicas and upstream provider latency can change the results.
4. If the candidate fails, pause sales writes and offline submission, preserve the current database and desktop queues, and capture the release, schema and external payment state. Switch the application and frontend to the prior compatible artifacts only after checking their migration and authorization assumptions. Restoring an old application that uses embedded checkpoint writes or lacks the regulated dispensing gate requires a separate reconciliation and security review.
5. If data recovery is required, restore to a separate verified instance, reconcile post-backup sales and provider payments, compare stock, ledger and settlement counts, then switch traffic. Keep original receipts and command IDs. Resume submissions only after a successful scoped smoke test and reconciliation.

The local drill ran the production Node entry point against a restored PostgreSQL database. The Catalyst Linux x86-64 package built with synthetic configuration. Hosted staging, Railway or Catalyst promotion, production rollback, database role replication, and provider and device checks remain release gates.
